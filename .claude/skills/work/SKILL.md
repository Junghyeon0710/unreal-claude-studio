# 카드 진행

작업 카드 한 장을 끝까지 진행한다: 구현 → 에디터 작업 → 테스트 → 검토 → 사장의 플레이 확인 → 마무리. 카드를 나누고 구현 방법을 정하는 것은 `cards` 스킬이 한다.

메인이 진행을 맡는다. C++ 구현은 메인이 직접 하고, 에디터 작업은 `ue-editor`, 테스트는 `ue-qa`, 검토는 `ue-reviewer`에게 맡긴다. 서브에이전트 브리프에는 카드 경로, 이번에 할 일, 관련 파일, 이전 결과가 적힌 곳을 넣는다.

## 시작

1. 인자: `$ARGUMENTS`
   - 카드 번호면 `docs/tasks/<번호>-*.md`를 연다.
   - 없으면 `진행 중`이나 `검토 중`인 카드를 이어서 한다. 그것도 없으면 다음 `대기` 카드를 추천한다(`cards` 스킬의 고르는 규칙).
2. 카드 상태를 본다.
   - `대기`: 구현 방법이 비어 있다. `cards` 스킬의 "카드 시작하기"부터 한다.
   - `진행 중`: "진행 기록"의 마지막 줄 다음 단계부터 한다. 대화가 바뀌었거나 요약됐으면 기억이 아니라 진행 기록과 `git status`를 믿는다.
   - `검토 중`: 5단계(플레이 확인)부터 한다.
   - `완료`: 끝난 카드라고 알린다.
3. 카드, 카드가 가리키는 기획서, `CLAUDE.md`를 읽는다.
4. 에디터가 켜져 있는지 확인한다(UE MCP가 응답하거나 `UnrealEditor.exe` 프로세스가 있음).

## 진행 기록

단계가 끝날 때마다 카드의 "진행 기록"에 한 줄을 쓴다. 대화가 끊겨도 이 기록으로 이어서 한다.

- 형식: `- YYYY-MM-DD: <단계> — <결과>` (예: `- 2026-11-12: 구현 — 끝, 빌드 성공`)
- 사장에게 묻지 않고 메인이 정한 것은 `판단:`으로 적는다. 무엇을 정했고, 왜, 틀리면 무엇을 다시 해야 하는지.

## 1. 구현

1. 카드의 "구현 방법"대로 C++을 쓴다. `.claude/rules/ue-cpp.md`를 따른다. 카드에 없는 구조 변경이 필요하면 멈추고 사장에게 묻는다.
2. `CLAUDE.md`의 규칙대로 컴파일한다.
   - 헤더, `UCLASS`/`UPROPERTY`/`UFUNCTION`, 새 파일을 바꿨으면 에디터가 꺼진 상태에서 `CLAUDE.md`의 빌드 명령.
   - `.cpp`만 바꿨고 에디터가 켜져 있으면 Live Coding.
3. 같은 에러로 3번 실패하면 멈추고 사장에게 보고한다.
4. 카드의 "바뀐 파일"을 채운다.

## 2. 에디터 작업

카드의 "에디터 작업"이 비어 있으면 건너뛴다.

1. 에셋을 여러 개 바꾸면 그 전에 지금 상태를 커밋할지 사장에게 묻는다.
2. `ue-editor`를 부른다. 브리프: 카드 경로, 에디터 작업 목록.
3. 보고를 처리한다.
   - 완료: 카드의 에디터 작업에 표시하고 "바뀐 파일"에 에셋 경로를 적는다. `ue-editor`는 카드를 쓰지 못한다.
   - 필요한 도구: `editor-tool-request` 스킬을 따른다.
   - 막힘: 에디터가 꺼져 있으면 켜 달라고 한 뒤 SendMessage로 같은 `ue-editor`에게 이어서 시킨다. 다른 질문은 메인이 답할 수 있으면 답하고, 아니면 사장에게 묻는다.

## 3. 테스트

1. 테스트를 새로 쓰거나 고치면 빌드가 필요하다. 에디터가 켜져 있으면 사장에게 저장하고 닫아 달라고 한다.
2. `ue-qa`를 부른다. 브리프: 카드 경로, 바뀐 파일, 이전 테스트 결과(카드의 "테스트 결과").
3. 보고를 처리한다.
   - 통과: 플레이 체크리스트가 카드의 "테스트 결과"에 있는지 확인하고 다음 단계로.
   - 실패: 게임 코드 문제면 메인이 고치고 같은 `ue-qa`에게 다시 돌리게 한다. 테스트의 기대값이 기획서와 다르면 기획서를 기준으로 정하고 `판단:`으로 적는다.
   - "ue-editor에게": 2단계 방법대로 `ue-editor`에게 만들게 하고 `ue-qa`를 이어서 시킨다.
   - 막힘: 방식을 정할 문제(예: 첫 Functional Test)면 추천과 함께 사장에게 묻는다.
4. 고치고 다시 돌리기는 3번까지. 그래도 실패하면 멈추고 사장에게 보고한다.

## 4. 검토

1. `ue-reviewer`를 부른다. 브리프: 카드 경로, 바뀐 파일(테스트 포함), 기획서.
2. 보고를 카드의 "검토 결과"에 적는다. `ue-reviewer`는 카드를 쓰지 못한다.
3. 처리한다.
   - 꼭 고칠 것: 메인이 고치고, `ue-qa`로 테스트를 다시 돌린 뒤, 같은 `ue-reviewer`에게 고친 부분만 다시 보게 한다. 3번까지.
   - 권장: 이 카드 범위 안에서 작게 고칠 수 있으면 고친다. 아니면 카드에 남겨 두고 마무리 때 보여 준다.
   - 확인 필요: 메인이 확인하고 결과를 적는다.
4. 통과하면 상태를 `검토 중`으로 바꾼다. 이제 사장의 플레이 확인을 기다린다.

## 5. 플레이 확인

1. 에디터가 꺼져 있으면 켜 달라고 하고, 확인할 것을 한 번에 준다: 카드의 "직접 플레이" 완료 조건과 플레이 체크리스트. 무엇을 하면 무엇이 보여야 하는지.
2. 사장의 답을 처리한다.
   - 좋음: 6단계로.
   - 값만 바꾸면 되는 것(기획서 "조절 값"의 범위 안): 바꾸고 다시 확인받는다. 바꾼 값과 이유를 진행 기록에 적는다. 기획서 기본값과 달라지면 마무리 때 기획서를 고칠지 묻는다.
   - 버그: 1단계로 돌아가 고친다. 테스트가 잡지 못한 경우면 `ue-qa`에게 그 경우의 테스트를 더하게 한다.
   - 규칙을 바꿔야 하는 것: 멈춘다. 기획서는 `/design`으로, 카드는 `cards` 스킬로 고친다.

## 6. 마무리

1. 카드: 완료 조건에 체크하고, 상태를 `완료`로, 진행 기록에 `완료`를 적는다.
2. 이 기능의 카드가 모두 `완료`면, 기능 기획서의 완료 조건이 모든 카드에서 체크됐는지 확인하고 게임 기획서 "첫 버전 기능"에서 이 기능에 체크만 한다. 기획서 내용은 바꾸지 않는다.
3. 이 기능의 카드가 모두 끝났으면 회고를 한다.
   - 이 기능 카드들의 진행 기록에서 `막힘`, `판단:`, 3번까지 간 고치기, 사장이 다시 설명해야 했던 곳을 모은다.
   - 그중 스튜디오(스킬, 에이전트, 규칙, 훅) 때문에 생긴 것만 골라 보여 주고, 사장에게 불편했던 점이 더 있는지 한 번 묻는다.
   - `docs/progress.md`의 "스튜디오 개선" 칸에 한 줄씩 적는다: 무엇이 불편했나 — 고칠 곳 후보. 스튜디오 파일은 여기서 바로 고치지 않고, 따로 상의해서 고친다.
4. `docs/progress.md`에 한 줄 적는다.
5. 사장에게 보여 준다: 바뀐 파일, 테스트 결과, 남겨 둔 권장, `판단:` 목록.
6. 커밋할지 묻는다. 커밋은 사장이 원할 때만 한다.
7. 다음을 알린다. 같은 기능에 남은 카드가 있으면 `/work`, 기능이 끝났으면 게임 기획서 "만들 순서"의 다음 기능 `/design <기능>`. 다음 카드는 새 대화에서 시작해도 된다.

## 사장에게 묻는 때

아래 경우만 멈추고 묻는다. 나머지는 메인이 정하고 `판단:`으로 적은 뒤 계속한다.

- 에디터를 켜거나 닫아 달라고 할 때. 메인과 에이전트는 에디터를 직접 끄지 않는다. 부탁은 꼭 필요할 때만, 한 번에 한다.
- 카드에 없는 구조 변경이나 기획서와 다르게 해야 할 때
- 새 도구를 만들 때(`editor-tool-request`), 에셋 여러 개를 바꾸기 전 커밋할지
- 같은 문제로 고치기가 3번을 넘을 때
- 플레이 확인, 커밋
