# 기획실

메인이 사장(사용자)과 대화하며 기획서를 쓴다. 메인은 묻고, 선택지와 추천을 내고, 정리해서 보여 준다. 결정은 사장이 한다.

기획서는 메인이 직접 쓴다. 사장에게 묻는 선택 창(AskUserQuestion)은 메인 대화에서만 쓸 수 있다. 서브에이전트는 확정 전 점검에만 쓴다.

기획서는 그것만 읽어도 이해되게 쓴다. 구현은 새 대화에서 기획서만 보고 시작할 수 있어야 하므로, 정한 것과 그 이유를 대화가 아니라 기획서에 남긴다.

## 시작

1. `CLAUDE.md`의 "게임" 칸과 `docs/design/`의 기획서를 읽는다.
2. 무엇을 쓸지 정한다. 인자: `$ARGUMENTS`
   - 인자가 `게임`이거나, 인자가 없고 "게임" 칸이 비어 있으면: 게임 기획서 `docs/design/game.md`. 양식은 이 스킬 폴더의 [game-template.md](game-template.md).
   - 기능 이름이면: 기능 기획서 `docs/design/<기능>.md`(영어 소문자와 `-`, 예: `dash.md`). 양식은 [feature-template.md](feature-template.md). 게임 기획서가 확정되지 않았으면 먼저 쓰자고 한다. 사장이 그냥 하자고 하면 진행하고 "살리는 재미"에 `(임시)`를 붙인다.
   - 인자가 없고 게임 기획서가 있으면: 무엇을 기획할지 묻는다. 게임 기획서의 "만들 순서"에서 아직 기획서가 없는 첫 기능을 추천한다.
   - 파일이 이미 있으면 처음부터 다시 쓰지 않는다. 읽고, 비어 있는 칸부터 이어서 한다.
3. 파일을 양식 그대로 먼저 만들고, 사장이 지금까지 한 말을 "내 말로"에 그대로 옮긴다. 정하지 않은 칸은 양식의 안내 문장을 남겨 둔다.
4. 사장에게 파일 경로와 몇 묶음으로 진행할지 한 줄로 알린다.

## 묻는 방법

- **한 번에 하나만 묻는다.** 다음 질문은 앞의 답을 보고 정한다.
- **처음에는 열린 질문으로** 사장이 원하는 것을 사장의 말로 듣는다. 예시 답을 붙이지 않는다.
- **고를 것이 생기면** AskUserQuestion으로 묻는다. 선택지는 2~3개, 장단점을 붙이고, 추천안을 첫 번째에 둔다. 질문만 하지 않고 의견을 낸다.
- **메인이 대신 고르지 않는다.** 사장이 "알아서 해"라고 하면 추천안을 쓰고 `(임시)`를 붙인다.
- **추측으로 채우지 않는다.** 모르는 것은 묻는다. 지금 정할 수 없으면 "열린 질문"으로 옮긴다.

## 한 묶음씩 진행

양식을 아래 묶음으로 나눈다. 묶음 안의 질문을 마치면:

1. **정리:** 이 묶음의 내용을 짧게(한 화면 안) 보여 준다.
2. **승인:** 같은 답에서 AskUserQuestion으로 "빠지거나 틀린 게 있나요?"(적기 / 고치기)를 묻는다. 글로만 묻지 않는다.
3. **쓰기:** 승인받은 묶음만 파일에 쓴다. 이 묶음에서 정한 것은 "결정과 이유"에 한 줄씩 남긴다(무엇을 골랐고 무엇을 버렸는지). 중간에 멈춰도 여기까지는 남는다.

묶음:

- 게임 기획서
  1. 한 줄 소개, 핵심 재미 3가지, 기본 정보
  2. 핵심 반복, 목표와 실패, 첫 1분
  3. 첫 버전 기능, 하지 않을 것, 피할 것, 만들 순서
  4. 참고 게임, 그만둘 조건
- 기능 기획서
  1. 한 줄 요약, 플레이어 경험
  2. 규칙, 상태
  3. 조절 값, 예외 상황
  4. 멀티플레이, 화면과 소리, 다른 기능과의 관계
  5. 완료 조건, 하지 않을 것

## 지킬 것

- **수치는 근거와 함께 낸다.** 예: "걷기 속도 600의 1.5배라서 900". 플레이해 봐야 아는 값은 "조절 값"에 넣고 범위를 적는다.
- **무엇을 하는지만 쓴다.** 클래스, 컴포넌트, 블루프린트와 C++ 중 어디에 둘지 같은 구현 방법은 쓰지 않는다. 구현 이야기가 나오면 "열린 질문"에 `(구현)`을 붙여 적고 작업 카드에서 정한다.
- **정확하게 쓴다.** 규칙과 예외 상황에 "적절히", "자연스럽게" 같은 말 대신 정확한 결과를 쓴다.
- **완료 조건은 확인할 수 있게 쓴다.** 규칙마다 하나 이상, 숫자나 눈에 보이는 결과가 있는 문장으로 쓴다. "재밌다"처럼 숫자로 못 나타내는 것은 "직접 플레이"로 표시하고 무엇을 볼지 적는다.
- **범위를 지킨다.** 첫 버전 기능이 7개를 넘거나 기능 하나가 너무 커지면 줄이자고 하고 뺄 것을 추천한다. 뺀 것은 "하지 않을 것"으로 옮긴다. 혼자 만들기 어려운 것(많은 아트, 복잡한 네트워크)은 그때그때 짚는다.
- **핵심 재미와 이어지게 한다.** 기능마다 어떤 핵심 재미를 살리는지 적는다. 어느 것도 살리지 않으면 사장에게 알린다.
- **사장이 싫다고 한 것을 지킨다.** 게임 기획서의 "피할 것"과 "내 말로"에 어긋나는 제안은 하지 않는다.
- **다른 기획서와 맞춘다.** 같은 수치나 규칙이 다른 기획서에 있으면 비교한다. 다르면 바로 알리고 어느 쪽이 맞는지 묻는다.
- **멀티플레이 게임이면** 기본은 서버가 확인하고 결정하는 것이다. 다른 플레이어에게 무엇이 보이는지, 두 플레이어가 동시에 하면 어떻게 되는지는 반드시 정한다.

## 확정 전 점검

모든 묶음을 쓰면 처음 보는 눈으로 점검한다. 쓴 쪽은 이미 당연하게 여기는 게 많아서 빈틈을 못 본다.

1. 읽기 전용 `Plan` 서브에이전트를 부른다(없으면 `general-purpose`에게 파일을 고치지 말라고 한다). 브리프:
   - 읽을 파일: 이 기획서와 `docs/design/game.md`만. 코드와 다른 문서는 읽지 않는다.
   - 할 일: 기능 기획서면 "이 기획서만 보고 작업 카드와 테스트를 만들 수 있는가", 게임 기획서면 "이것만 보고 첫 기능을 기획할 수 있는가". 막히는 곳, 서로 어긋나는 곳, 확인할 수 없는 완료 조건을 찾는다.
   - 보고: 항목마다 "어느 칸 — 무엇이 빠졌나 — 왜 필요한가". 답을 정하거나 파일을 고치지 않는다.
2. 기획서에 이미 답이 있는 항목은 버린다. 남은 항목은 사장에게 하나씩, 추천과 함께 묻는다.
3. 답을 기획서와 "결정과 이유"에 반영한다.

## 확정

1. 기획서 전체를 보여 주고 확정할지 묻는다.
2. 확정하면 상태를 `확정`으로, 마지막 수정 날짜를 오늘로 바꾼다.
3. 게임 기획서면 `CLAUDE.md`의 "게임" 칸에 한 줄 소개, 핵심 재미 3가지, 기획서 경로를 적는다.
4. `docs/progress.md`에 한 줄 적는다.
5. 다음 단계를 알린다. 게임 기획서면 "만들 순서" 1번 기능의 기획, 기능 기획서면 `/cards <기능>`으로 작업 카드 만들기. 작업 카드와 구현은 새 대화에서 기획서를 보고 시작해도 된다고 알린다.

## 확정된 기획서를 바꿀 때

1. 바꿀 칸의 전과 후를 보여 주고 승인받는다.
2. `docs/tasks/`에서 이 기획서를 가리키는 작업 카드를 찾아, 영향받는 카드가 있으면 알린다. 카드는 `/cards`의 "기획서가 바뀌었을 때"대로 고친다.
3. "결정과 이유"를 고치고, 마지막 수정 날짜를 바꾸고, "바뀐 기록"에 날짜와 한 줄을 남긴다.
