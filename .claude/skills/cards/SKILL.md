# 작업 카드

기능 기획서를 에이전트가 바로 일할 수 있는 작업 카드로 나눈다. 기획서는 무엇을 하는지만 적었으므로, 어떻게 만들지는 여기서 정한다. 카드를 실제로 진행하는 것(구현 → 에디터 → 테스트 → 검토)은 이 스킬이 하지 않는다.

카드는 메인이 직접 쓴다. 구조를 정하는 선택은 사장에게 묻는다. 선택 창(AskUserQuestion)은 메인 대화에서만 쓸 수 있다.

카드 한 장만 읽어도 일할 수 있게 쓴다. `ue-programmer`, `ue-editor`, `ue-qa`, `ue-reviewer`는 카드와 카드가 가리키는 기획서만 보고 일한다.

## 시작

1. 인자: `$ARGUMENTS`
   - 기능 이름이면 `docs/design/<기능>.md`를 읽는다. 없거나 상태가 `확정`이 아니면 멈추고 `/design <기능>`부터 하자고 한다.
   - 인자가 없으면 `docs/tasks/`에서 `대기` 카드가 남은 기능을 추천한다. 없으면 확정됐지만 카드가 없는 기획서를 추천한다.
   - 기획서 없이 할 작은 변경이나 버그면 "작은 변경과 버그"를 한다.
2. `docs/tasks/`에서 이 기획서를 가리키는 카드를 찾는다.
   - 없으면 "카드 나누기"를 한다.
   - 있으면 "카드 시작하기"를 한다. `대기` 카드 중 먼저 끝나야 할 카드가 모두 `완료`인 것에서 번호가 가장 작은 것을 고른다.
3. `CLAUDE.md`와 `.claude/rules/ue-cpp.md`, 그리고 관련 코드를 읽는다. 기획서의 "다른 기능과의 관계"에 나온 기능은 그 카드와 코드도 읽는다.

## 작은 변경과 버그

기획서 전체를 쓰기엔 작은 일은 기획서 없이 카드 한 장으로 한다.

- 쓰는 때: 조절 값 바꾸기, 버그 고치기, 이미 있는 기능에 작은 동작 더하기. 카드 한 장으로 끝나는 일.
- 쓰지 않는 때: 새 기능, 확정된 기획서의 규칙이 바뀌는 일, 카드가 2장 넘게 필요해 보이는 일. 이때는 `/design`부터 한다.

1. 무엇을 왜 바꾸는지 한 줄로 정리한다. 버그면 재현 순서, 기대한 결과, 실제 결과를 받는다. 모르면 묻는다.
2. 관련 기획서가 있으면 읽는다. 기획서 "조절 값"의 범위 안이면 그대로 한다. 범위를 벗어나거나 규칙이 바뀌면 멈추고 `/design`으로 기획서부터 고치자고 한다.
3. 카드를 만든다.
   - 파일: 버그는 `docs/tasks/NNN-<기능>-fix-<이름>.md`, 작은 변경은 `docs/tasks/NNN-<기능>-<이름>.md`.
   - 기획서 칸: 관련 기획서 경로, 없으면 `없음 (작은 변경)`.
   - 할 일: 무엇을 왜 바꾸는지. 버그면 재현 순서, 기대한 결과, 실제 결과도.
   - 완료 조건: 메인이 써서 사장에게 확인받는다. 버그면 "재현 순서대로 하면 기대한 결과가 나온다"를 넣고, 가능하면 그 버그를 다시 잡는 자동 테스트를 테스트 계획에 넣는다.
4. 목록 승인 없이 바로 "카드 시작하기"를 한다.

## 카드 나누기

1. 기획서의 완료 조건을 순서대로 번호를 붙여 본다(1, 2, 3...).
2. 카드로 묶는다.
   - 카드 하나는 혼자 확인할 수 있는 결과(자동 테스트나 직접 플레이)로 끝난다.
   - 나누는 기준: 검토자가 이 카드만 따로 "다시 해"라고 할 수 있는 단위. 준비 작업(폴더, 설정, 입력 에셋)은 따로 카드로 빼지 않고 그것이 필요한 카드에 넣는다.
   - 기능 하나에 보통 2~5장. 한 장으로 충분하면 한 장. 5장을 넘으면 기획서가 너무 크다고 사장에게 알린다.
   - 순서: 손으로 해 볼 수 있는 핵심 동작을 먼저, 이펙트와 소리 같은 겉모습은 뒤로.
   - 완료 조건은 모두 정확히 한 카드에 들어간다.
3. 승인받는다.
   - 2장 이상이면: 목록을 표로 보여 주고(카드 / 하는 것 / 맡는 완료 조건 / 확인 방법 / 먼저 끝나야 할 카드), 같은 답에서 AskUserQuestion으로 승인받는다(이대로 / 고치기).
   - 1장이면: 목록 승인을 건너뛴다. 카드 파일을 만들고 바로 "카드 시작하기"로 간다. 사장은 카드 전체를 볼 때 한 번에 확인한다.
4. 카드 파일을 모두 만든다.
   - 파일: `docs/tasks/NNN-<기능>-<이름>.md`(영어 소문자와 `-`). NNN은 `docs/tasks/` 전체에서 다음 번호(세 자리).
   - 양식: [card-template.md](card-template.md)
   - 지금 채우는 칸: 머리(상태 `대기`), 할 일, 완료 조건, 하지 않을 것. "구현 방법"부터는 양식의 안내 문장을 그대로 둔다.
5. 첫 카드를 바로 시작할지 묻는다(1장이면 묻지 않고 시작한다).

## 카드 시작하기

앞 카드를 만들어 보면 뒤 카드 계획이 바뀌는 일이 많다. 그래서 구현 방법은 카드를 시작할 때 정한다.

1. 먼저 끝난 카드들의 "바뀐 파일", "다음 카드가 쓰는 것", "진행 기록"을 읽고, 실제 코드에서 그 이름이 맞는지 확인한다.
2. 구현 방법을 정한다.
   - **구조를 정하는 선택은 사장에게 묻는다.** AskUserQuestion으로 선택지 2~3개, 장단점, 추천안을 첫 번째에 둔다. 예: 새 컴포넌트를 만들지 캐릭터에 넣을지, C++로 할지 블루프린트로 할지, 엔진 기능 중 무엇을 쓸지. 추천은 `.claude/rules/ue-blueprint-cpp.md`(C++와 블루프린트 나누기)와 `.claude/rules/ue-cpp.md`의 "구조와 의존성"을 따른다.
   - **작은 것은 메인이 정한다.** 파일 위치, 함수 이름처럼 규칙과 기존 코드로 정해지는 것.
   - 기획서 "열린 질문"의 `(구현)` 항목 중 이 카드에 해당하는 것은 여기서 답한다.
3. 카드의 칸을 채운다.
   - **구현 방법:** 만들거나 바꿀 파일, 클래스와 함수 이름(매개변수와 반환형), C++와 블루프린트 나눔, 기획서 조절 값을 어디에 둘지. 함수 본문 코드는 쓰지 않는다. 이름과 테스트만으로 정해지지 않는 계산 방법만 한 줄로 적는다.
   - **앞 카드에서 쓰는 것 / 다음 카드가 쓰는 것:** 정확한 이름과 형. 다음 카드는 이 칸만 보고 이름을 안다.
   - **에디터 작업:** `ue-editor`에게 넘길 목록. 에셋 경로와 이름까지(`.claude/rules/ue-assets.md`).
   - **테스트 계획:** 완료 조건마다 하나.
     - 자동 테스트: 테스트 이름과 확인할 값. Automation Spec이면 `<프로젝트>.<기능>.<동작>`(`CLAUDE.md`의 테스트 이름 규칙). 월드가 필요한 Functional Test면 테스트 맵 경로(`/Game/Tests/...`)와 그 맵 안의 테스트 이름.
     - 직접 플레이: 무엇을 해서 무엇이 보여야 하는지.
   - **결정과 이유:** 이 카드에서 정한 구현 선택마다 한 줄. 고른 것과 버린 것.
4. 아래 "점검"을 한다.
5. 카드 전체를 보여 주고 승인받는다. 승인되면 상태를 `진행 중`으로 바꾸고 "진행 기록"에 날짜와 "시작"을 적는다.
6. 다음 단계를 알린다: `/work <카드 번호>`로 구현부터 마무리까지 진행한다. 새 대화에서 이 카드만 보고 시작해도 된다고 알린다. `/work`가 `대기` 카드로 시작하면 이 "카드 시작하기"부터 한다.

## 점검

카드를 다 쓰면 스스로 확인하고, 고칠 것은 바로 고친다.

- **빠짐:** 기획서 완료 조건이 모두 정확히 한 카드에 있는가(나누기 때). 이 카드의 완료 조건마다 테스트 계획이 있는가.
- **모호함:** 줄마다 만들 수 있는 것이 하나로 정해지는가. "적절히", "필요하면", "나중에 정함" 같은 줄이 없는가.
- **이름:** "앞 카드에서 쓰는 것"이 앞 카드의 "다음 카드가 쓰는 것"과 글자까지 같은가. 같은 것을 두 이름으로 부르지 않는가.
- **범위:** 기획서 "하지 않을 것"이나 다른 카드가 맡은 완료 조건을 만들지 않는가.
- **크기:** 카드가 만들 코드보다 길지 않은가. 함수 본문이 들어갔으면 이름과 확인 값만 남긴다.

## 지킬 것

- **기획서를 바꾸지 않는다.** 기획서와 다르게 해야 하거나 기획서가 모자라면 멈추고 사장에게 알린다. 기획서는 `/design`으로 고친다.
- **추측하지 않는다.** 모르는 것은 사장에게 묻거나 코드에서 확인한다. 엔진 API는 엔진 소스에서 실제 선언을 확인하고 쓴다.
- **숫자는 기획서에서 그대로 가져온다.**
- **상태:** `대기 → 진행 중 → 검토 중 → 완료`. 이 스킬은 `대기`와 `진행 중`만 쓴다.

## 기획서가 바뀌었을 때

`/design`이 확정된 기획서를 바꿔서 영향받는 카드가 있으면:

- `대기` 카드: 할 일과 완료 조건을 다시 쓴다.
- `진행 중`이나 `완료` 카드: 바뀐 점을 "진행 기록"에 적고, 새 카드를 만들지 사장에게 묻는다.
